## 2. PDRとは何か

PDRは `Pedestrian Dead Reckoning` の略で、歩行者がどこへ移動したかをセンサから積み上げて推定する方法です。

最小限の考え方は次の式です。

```text
新しい位置 = 前の位置 + 1歩の移動量
```

2次元平面で、1歩の長さを `l`、向いている方位を `h` とすると、本プロジェクトでは次のように位置を更新します。

```python
x += l * sin(h)
y += l * cos(h)
```

この座標系では次の意味になります。

| 方位 `h` | 移動方向 |
| ---: | --- |
| `0 deg` | `+y` 方向、図の上方向 |
| `90 deg` | `+x` 方向、図の右方向 |
| `-90 deg` | `-x` 方向、図の左方向 |

したがって、軌跡を作るために必要なのは主に次の3要素です。

| 要素 | 意味 | 間違った場合の軌跡への影響 |
| --- | --- | --- |
| 歩数検出 | いつ1歩進んだか | 点が多すぎる、少なすぎる |
| 歩幅推定 | 1歩で何m進むか | 軌跡全体が大きすぎる、小さすぎる |
| 方位推定 | その歩をどちらへ進めるか | 直線が曲がる、角が歪む、閉路が閉じない |

今回の調査では、歩数と距離は概ね妥当だった一方、方位が軌跡を大きく崩していました。そのため、改善の中心は方位推定です。

## 4. シンプル版の処理

比較図のオレンジ線 `simple (legacy)` は、補正導入前の考え方を再現するものです。

設定は [`config.yaml`](../config.yaml) の `comparison.simple` に明示されています。

```yaml
comparison:
  simple:
    acc_smoothing_window: 10
    height: 12.0
    distance_s: 0.35
    prominence: 0.4
    gyro_axis: "z"
    gyro_sign: -1.0
    use_bias_correction: true
    bias_static_duration_s: 2.0
    step_length_m: 0.65
```

### 4.1 歩数検出

シンプル版では、加速度3軸の大きさを計算します。

```text
acc_norm = sqrt(acc_x^2 + acc_y^2 + acc_z^2)
```

端末がどの方向を向いていても加速度の大きさは得られるため、実装は簡単です。しかし、歩行で重要な「上下方向の揺れ」だけでなく、端末を振った成分や横方向の成分も混ざります。

### 4.2 方位推定

シンプル版では、ジャイロの端末座標系 `z` 軸だけを積分します。

```text
heading = integral(-gyro_z)
```

この方法は、端末の `z` 軸が常に鉛直に近い場合には分かりやすく動きます。しかし、端末が傾いた場合、歩行者が水平面で回転した成分と端末の `gyro_z` は一致しません。

### 4.3 歩幅

全ステップを固定歩幅で進めます。Data2のシンプル比較では主に `0.65m` を使用しています。

### 4.4 シンプル版の利点と限界

| 利点 | 限界 |
| --- | --- |
| 処理が小さく理解しやすい | 端末の傾きに弱い |
| 磁気ノイズを受けない | ジャイロドリフトが蓄積する |
| 今回の比較基準として使いやすい | 曲がりの再現や閉路に誤差が出る |

## 5. 参照したSmartPDRの考え方

Qiita記事およびGitHub実装では、主に次の流れで軌跡を求めています。

```text
端末座標系の加速度をグローバル座標系へ変換
  ↓
鉛直加速度をHPF/LPF処理してステップを検出
  ↓
ジャイロをグローバル鉛直軸へ変換して方位を積分
  ↓
磁気センサ由来の方位を用いてジャイロ方位を判断
  ↓
ステップ長と方位で位置を更新
```

### 5.1 なぜ座標変換が必要か

スマートフォンの軸は端末に固定されています。

例えば、手に持って水平にしているときの `z` 軸と、少し傾けて持ったときの `z` 軸は、地面に対して同じ方向ではありません。

一方、歩行検出や水平面の旋回で本当に知りたいのは、地面を基準にした次の成分です。

- 鉛直方向の上下動
- 鉛直軸まわりの回転

SmartPDRでは、端末座標系から地面基準のグローバル座標系へ変換することで、この問題を扱います。

### 5.2 参照実装のステップ検出

参照実装 `useAccStep` は、以下の処理を行います。

1. 姿勢を用いて加速度をグローバル座標系へ変換する
2. 鉛直加速度にHPFを適用する
3. 移動平均を取る
4. `peak`、`peak-to-peak`、`slope` の3条件でステップを判定する

記事・実装で示される主なパラメータは次の通りです。

| パラメータ | 値 |
| --- | ---: |
| 移動平均窓 `W` | `3` |
| 判定窓 `N` | `6` |
| HPF係数 `alpha` | `0.95` |
| ピーク閾値 | `0.5 m/s^2` |
| peak-to-peak閾値 | `1.0 m/s^2` |

### 5.3 参照実装の方位推定

参照実装 `useHeading` は、概ね次を行います。

1. 磁気センサを姿勢補償し、磁気方位 `h_mag` を求める
2. ジャイロベクトルを重力方向へ射影し、水平面での旋回速度を得る
3. 旋回速度を積分し、ジャイロ方位 `h_gyr` を得る
4. 磁気方位とジャイロ方位の一致度、磁気方位の変動量から、採用する方位を決める

参照実装では、次のような4分岐の重み付き計算を使用しています。

```text
磁気とジャイロが一致し、磁気も安定     -> 前回値 + 磁気 + ジャイロ
磁気とジャイロが一致し、磁気が変化     -> 磁気 + ジャイロ
磁気とジャイロが不一致で、磁気が安定   -> 前回値
磁気とジャイロが不一致で、磁気が変化   -> 前回値 + ジャイロ
```

### 5.4 参照実装の位置更新

GitHubの `location.js` では、位置更新は次の構造です。

```javascript
nx = stepLength * Math.sin(headingStep)
ny = stepLength * Math.cos(headingStep)
```

本プロジェクトの `x`、`y` 更新もこの形に合わせています。

## 6. 現在の補正版の処理全体

補正版の実行フローは [`pdr_visualizer/trial.py`](../pdr_visualizer/trial.py) にまとまっています。

```text
1. センサCSVを読み込む
2. 鉛直歩行信号を生成する
3. ステップを検出する
4. SmartPDR風方位を推定する
5. 歩幅を付与する
6. 初期直進アライメントを適用する
7. 軌跡を生成する
8. シンプル版も別に計算して比較図を生成する
```

現在の主設定は次の通りです。

```yaml
preprocessing:
  acc_smoothing_window: 3
  step_signal: "vertical_hpf"
  hpf_alpha: 0.95

heading:
  use_smart_pdr: true
  h_cor_t_deg: 5.0
  h_mag_t_deg: 2.0
  mag_correction_gain: 0.05
  use_bias_correction: true
  bias_static_duration_s: 1.0
  initial_alignment:
    enabled: true
    step_count: 6
    target_heading_deg: 0.0

pdr:
  step_length_mode: "fixed"
  step_length_m: 0.60
```

## 7. 再現できている部分

ここでいう「再現できている」とは、記事・GitHub実装が目的としている処理を、現在のPythonコードでも同じ考え方で実施していることを意味します。

### 7.1 鉛直方向の歩行信号生成

実装箇所: [`processing.py` の `add_acc_norm`](../pdr_visualizer/processing.py)

補正版では `Gravity.csv` の重力ベクトルを単位化し、加速度との内積を取ります。

```text
acc_vertical = acceleration dot unit_gravity
```

これにより、端末が多少傾いても、歩行の上下動に対応する成分を取り出せます。

その後、記事と同じ目的で低周波の重力成分を取り除きます。

```text
gravity_component[t]
    = alpha * gravity_component[t-1]
      + (1 - alpha) * acc_vertical[t]

acc_vertical_hpf = acc_vertical - gravity_component
```

`alpha` は記事の値に合わせて `0.95` です。

### 7.2 ステップ検出用信号の移動平均

記事の `W=3` に合わせ、補正版では鉛直HPF信号を3点移動平均で平滑化します。

```yaml
preprocessing:
  acc_smoothing_window: 3
```

### 7.3 ジャイロの鉛直軸射影

実装箇所: [`processing.py` の `_estimate_heading_smart_pdr`](../pdr_visualizer/processing.py)

参照実装は、補正済みジャイロベクトルを重力方向へ射影して、グローバル座標系の鉛直軸まわり回転を求めます。

現在の実装も同じ目的で次を計算します。

```text
vertical_rate = gyro_vector dot unit_gravity
```

シンプル版の `gyro_z` 一本だけを積分する方法より、端末の傾きの影響を抑えられます。

### 7.4 磁気センサを使った方位検証

現在の実装では、重力ベクトルから `pitch`、`roll` を求め、磁気ベクトルを水平面へ補償して磁気方位を計算しています。

また、ジャイロ方位と磁気方位が近く、磁気方位の時系列変化も小さい場合のみ、磁気情報を補正に使います。

```python
correlated = abs(error) <= h_cor_t_rad
magnetically_stable = abs(mag_delta) <= h_mag_t_rad
accepted = correlated and magnetically_stable
```

これは「磁気センサを常に信用せず、妥当な場合にだけ利用する」というSmartPDRの中心的な発想を再現しています。

### 7.5 位置更新

実装箇所: [`processing.py` の `build_trajectory`](../pdr_visualizer/processing.py)

次の位置更新式は、参照実装と同じ構造です。

```python
x += step_length_m * np.sin(heading)
y += step_length_m * np.cos(heading)
```

### 7.6 動的歩幅モデルの式

記事で示される以下の2式は、切替可能な処理として実装されています。

```text
4乗根モデル: l = gamma * fourth_root(acc_pp) + delta
対数モデル:  l = gamma * log(acc_pp) + delta
```

係数も設定に保持されています。

```yaml
dynamic_step_length:
  acc_threshold: 3.23
  fourth_root_gamma: 1.479
  fourth_root_delta: -1.259
  log_gamma: 1.131
  log_delta: 0.159
```

ただし、後述の通り、現在の既定軌跡では動的歩幅は使用していません。

## 8. 記事・GitHub実装から変更した部分

現在の実装は、完全なコード移植ではありません。入力データの形式と実測結果に合わせて、いくつか意図的な変更をしています。

### 8.1 姿勢推定ではなく `Gravity.csv` を利用

| 参照実装 | 現在のPython実装 |
| --- | --- |
| 加速度・磁気等から姿勢角を計算し、回転行列でGCSへ変換 | phyphoxの `Gravity.csv` を利用して鉛直方向へ直接射影 |

目的は同じです。どちらも「端末が傾いても鉛直方向の成分を取り出す」ための処理です。

変更した理由は次の通りです。

- 今回の記録には既に `Gravity.csv` が存在する
- センサアプリ側で算出された重力方向を使う方が、オフラインCSV解析では簡潔で再現しやすい
- 姿勢角の符号や端末座標系の解釈ミスを減らせる

したがって、数学的目的は再現していますが、参照実装の姿勢推定コードをそのまま再現しているわけではありません。

### 8.2 記事の3条件ステップ検出を既定値では使用していない

参照実装の `peak`、`peak-to-peak`、`slope` 判定は [`processing.py`](../pdr_visualizer/processing.py) の `_detect_steps_custom` として実装されています。

しかし、実測データで既定として使ったところ、`Data2/001_walk` の歩数を取りこぼしました。直進6mで必要な約10歩に届かず、距離評価そのものを悪化させたため、現在は次を既定にしています。

```yaml
step_detection:
  use_custom_algorithm: false
```

現在の既定は、SmartPDR風に作成した鉛直歩行信号に対して `scipy.signal.find_peaks` を適用する方法です。

つまり、

- 入力信号の作り方はSmartPDR風
- ピーク判定器は実データに適した既存方式

という組み合わせです。

### 8.3 方位融合を4分岐重み付き平均から変更

参照実装では、磁気方位とジャイロ方位を4条件により重み付き平均します。

最初の再現実装では、この方針を角度値に対して直接適用していました。しかし角度には次の問題があります。

```text
359 deg と 1 deg は実際には近い
通常の数値差では 358 deg 離れていると扱われる
```

これにより、`0 deg / 360 deg` 境界をまたぐと方位が大きく飛び、軌跡が破綻しました。

現在の実装は、円周角として安全な差を計算します。

```python
angle_difference = angle(exp(1j * (target - reference)))
```

そして、磁気とジャイロが十分近く、磁気変化も安定している場合にだけ、小さな割合で磁気方位へ寄せます。

```python
heading = predicted + 0.05 * magnetic_error
```

| 項目 | 参照実装 | 現在の実装 |
| --- | --- | --- |
| 判断材料 | 磁気・ジャイロ相関、磁気変化 | 同じ |
| 補正方法 | 条件別の重み付き平均 | ジャイロ予測に磁気誤差の5%を加算 |
| 角度境界対応 | JavaScript実装のまま | 円周角差で明示的に安全化 |

この変更は、記事の意図である「磁気をvalidationとして使う」は維持しつつ、今回観測された軌跡破綻を防ぐための実装上の改良です。

### 8.4 ジャイロバイアス補正を初期1秒の平均に変更

参照実装では、磁気方位が安定している期間に応じてジャイロバイアスを更新します。

現在の実装では、記録冒頭の静止していると考えられる区間の平均をバイアスとします。

```yaml
heading:
  bias_static_duration_s: 1.0
```

元々 `2.0s` 以上を使うと、今回のデータではすでに歩行や方向変化が始まったサンプルを含み、本来の回転成分までバイアスとして差し引く可能性がありました。そのため、実測した歩行開始時刻に合わせて `1.0s` に短縮しています。

これは簡潔で検証しやすい一方、計測開始直後からすでに動いているデータでは正しく機能しません。

### 8.5 動的歩幅モデルを実装したが、既定では固定歩幅

参照実装は動的歩幅を利用します。現在の実装にも動的歩幅の式はありますが、既定設定では次のように固定歩幅を使います。

```yaml
pdr:
  step_length_mode: "fixed"
  step_length_m: 0.60
```

理由は、今回の主要な問題が方位であることが分かったためです。方位と歩幅を同時に変更すると、軌跡が改善または悪化した原因を判断しにくくなります。

現在は、

```text
まず方位の形を評価するため固定歩幅
方位が安定した後に動的歩幅の評価へ進む
```

という切り分け方針です。

## 9. 今回追加した「初期直進アライメント」

### 9.1 観測された問題

SmartPDR風補正を導入した結果、長方形の閉じ方は非常に改善しました。一方、補正版には次の特徴が見られました。

```text
本当は最初に +y 方向へまっすぐ歩いている
しかし、表示された軌跡は最初から少し -x 側へ傾く
```

補正前のSmartPDR風軌跡で、最初の直線部分の `x` 位置を集計すると次のようになりました。

| データ群 | 初期直線終了付近の平均 `x` |
| --- | ---: |
| Data2 手持ち | `-0.481m` |
| Data3 手持ち | `-0.788m` |

これは、推定された開始方位が表示座標系の `0 deg` よりも、平均して数度左へ向いていることを意味します。

### 9.2 なぜ起こるか

SmartPDRの方位は、端末が向いている方位とセンサから得られる方位を基準にします。

しかし今回の可視化では、実験コースの都合として、

```text
最初の直線は必ず図の +y 方向として描きたい
```

という別の基準があります。

この2つの基準は必ずしも一致しません。

原因として考えられるものは次の通りです。

- 歩行開始時に端末が身体正面から数度傾いていた
- 磁気方位がコースの描画軸と数度ずれていた
- 初期方位を相対化した時点が、歩行者の実際の直進向きと完全には一致しなかった

重要なのは、これは必ずしも「歩行者が本当に左へ歩いた」という意味ではなく、推定方位の基準と描画したい実験座標系が数度ずれている可能性が高いということです。

### 9.3 補正の考え方

今回のコースでは、最初の数歩が直進であり、その方向が `0 deg`、つまり図の `+y` 方向であることが分かっています。

そこで、最初の6歩で推定された方位の平均を取り、その平均が `0 deg` になるよう、軌跡全体の方位を回転させます。

処理は [`processing.py` の `align_heading_to_initial_steps`](../pdr_visualizer/processing.py) にあります。

### 9.4 計算方法

単純に角度の算術平均を取ると、`179 deg` と `-179 deg` のような角度境界で問題が起こります。そのため、円周平均を使います。

最初の `K=6` 歩の方位を次のように表します。

```text
h_1, h_2, ..., h_6
```

円周平均方位 `h_mean` は概念的に次です。

```text
h_mean = angle(mean(exp(j * h_k)))
```

今回の目標方向は `h_target = 0 deg` です。したがって補正量は、

```text
offset = h_mean - h_target
```

となります。

全時刻の方位から同じ `offset` を引きます。

```text
h_aligned(t) = h_original(t) - offset
```

この処理は、軌跡の形を無理に曲げたり各辺を別々に調整するものではありません。全体を一つの角度だけ回転し、開始直線を実験座標系に合わせる処理です。

### 9.5 設定

設定は次の通りです。

```yaml
heading:
  initial_alignment:
    enabled: true
    step_count: 6
    target_heading_deg: 0.0
```

| 設定 | 意味 |
| --- | --- |
| `enabled` | 初期直進アライメントを使うか |
| `step_count` | 初期方向を推定するために使う歩数 |
| `target_heading_deg` | 最初の直線を図上でどの方向へ合わせるか |

### 9.6 補正前情報の保持

補正を適用すると、元々センサ融合で推定された方位を見失ってしまう危険があります。そのため、`heading.csv` には補正前と補正後の両方を保存します。

| 列名 | 意味 |
| --- | --- |
| `heading_rad` | 初期直進アライメント適用後の方位 |
| `heading_rad_unaligned` | アライメント適用前の方位 |
| `heading_gyro_rad` | アライメント適用後のジャイロ方位 |
| `heading_gyro_rad_unaligned` | 適用前のジャイロ方位 |
| `heading_mag_rad` | アライメント適用後の磁気方位 |
| `heading_mag_rad_unaligned` | 適用前の磁気方位 |
| `heading_alignment_offset_rad` | 全体へ適用した回転オフセット |

これにより、補正結果だけでなく、元のセンサ推定がどうずれていたかも検証できます。

### 12.1 SmartPDR参照実装の完全移植ではない

現在は、記事・GitHub実装の主要な考え方を取り入れたPythonオフライン解析です。React Nativeフックの状態更新順、100ms更新、姿勢算出、4分岐融合をそのまま逐一再現したものではありません。

### 12.2 動的バイアス推定

参照実装の磁気安定区間に基づくジャイロバイアス更新は未実装です。現在は初期1秒の平均バイアスです。

将来的には、次の比較が必要です。

- 初期静止を十分確保したデータでの固定バイアス
- 磁気安定区間を用いた動的バイアス
- 直進データでの時間経過ドリフト

### 12.3 動的歩幅の既定適用

動的歩幅モデルは実装されていますが、現在は方位検証を優先して固定歩幅を利用しています。

方位が安定した後、次の順で評価するのが安全です。

1. 固定歩幅で軌跡形状を評価
2. 動的歩幅を有効化
3. 距離誤差と閉路誤差を比較

### 12.4 ポケット条件

ポケット条件では、端末が身体正面を向いているとは限りません。

例えば、歩行者が正面へ進んでいても、ポケット内の端末上端が斜めや横へ向いていれば、端末方位と歩行者方位は一致しません。

この問題は参照記事でも制約として述べられています。現在の初期直進アライメントだけでは、歩行中に端末姿勢が変わるポケット条件を一般的に解決できません。

必要になる可能性のある方法は次の通りです。

- 手持ちとポケットを別モードとして扱う
- 身体進行方向に対する端末の装着角オフセットを校正する
- 歩行周期と加速度水平成分から身体方向を推定する
- 地図や既知通路方向による補正を併用する

## 13. 今回の補正手法はどの場合に使えるか

### 13.1 有効に使える場合

初期直進アライメントは、次の条件を満たす場合に有効です。

| 条件 | 例 |
| --- | --- |
| 記録開始後に、進行方向が既知の直線区間がある | 最初に廊下を北向きに6m歩く |
| その直線区間で端末姿勢が概ね一定 | 手持ちで正面付近に保つ |
| 軌跡を実験用座標系へ揃えたい | 最初の直線を図の `+y` に揃える |
| 誤差の中心が一定の初期方位オフセットである | 全軌跡が数度だけ斜めに回転している |

この場合、全軌跡を一つの角度だけ回転することは合理的です。旋回角や相対的な形状を大きく変えず、表示座標系とのずれを除去できます。

### 13.2 適用してはいけない、または注意が必要な場合

| 場合 | なぜ危険か |
| --- | --- |
| 最初から曲がって歩く経路 | 最初の平均方位を直線と誤認する |
| 開始方向が未知 | `target_heading_deg` を決められない |
| 最初の6歩で端末を持ち替える | 初期方位平均が身体方向を表さない |
| ポケット内で端末が回転する | 定数オフセットだけでは直せない |
| 本当に歩行者が斜めに歩いた | 実際の動きを誤って真っ直ぐへ補正する |

### 13.3 一般性について

この補正には、限定的な一般性があります。

#### 一般性がある部分

「既知方向の初期直線を使って座標系を合わせる」という考え方は、多くのPDR実験で使えます。

例えば、

- 開始地点で矢印方向へ数m直進してから自由歩行する
- 建物入口から既知の廊下方向へ進む
- ロボットや歩行者に初期キャリブレーション動作を要求する

といった運用であれば、同じ手法を適用できます。

#### 一般性がない部分

この補正は、任意の歩行軌跡をセンサだけで自動的に正しい絶対方向へ直す方法ではありません。

補正が利用しているのは、

```text
最初の数歩は真っ直ぐで、その正解方向が分かっている
```

という外部知識です。

したがって、未知の屋内経路、自由歩行、ポケット内で動く端末などに対して、そのまま万能に使える補正ではありません。

分類すると、今回の補正は次の位置づけです。

| 分類 | 該当するか |
| --- | --- |
| センサの生データのみから絶対方位を改善する手法 | いいえ |
| 実験コースの既知条件を利用した初期座標系校正 | はい |
| 手持ち固定に近い条件での再現性向上 | はい |
| ポケット条件を一般的に解決する手法 | いいえ |

## 16. 結論

本プロジェクトでは、単純な `acc_norm + gyro_z` による軌跡生成から、次の段階まで改善しました。

1. 重力方向に基づく鉛直歩行信号の利用
2. ジャイロの鉛直軸射影
3. 傾き補償した磁気方位によるジャイロ方位のvalidation
4. シンプル版との比較図出力
5. 既知の初期直線を使った座標系アライメント

記事・GitHub実装の中心的な考え方である、

```text
鉛直信号で歩行を捉え、
ジャイロの回転を磁気で検証し、
ステップごとに位置を更新する
```

という構造は再現しています。

一方で、現在の実装は次の点で実験データに合わせた変更を含みます。

- `Gravity.csv` を用いた直接的な鉛直射影
- `find_peaks` による既定ステップ検出
- 円周角差と小ゲイン補正による磁気validation
- 初期1秒に限定したジャイロバイアス
- 固定歩幅による方位評価
- 初期直進が既知であることを利用した全体回転補正

特に今回追加した初期直進アライメントは、直進データおよび手持ち条件の初期区間を大きく改善しましたが、未知方向の自由歩行やポケット条件を一般的に解くものではありません。

次の改善課題としては、次が有力です。

1. 初期アライメント有無を自動評価する診断出力
2. ポケット条件の端末方向と身体方向の関係推定
3. 固定歩幅から動的歩幅への段階的な評価
4. 旋回区間・直進区間ごとの誤差集計

現時点では、開始方向が既知で端末を概ね正面に保持する実験に対して、補正版はシンプル版より形状・直進性・閉路性を評価しやすい軌跡を生成できています。
